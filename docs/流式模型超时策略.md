# 流式模型超时策略（0.1.25）

## 原因与修复

原实现同时为 JDK HTTP 客户端及流式看门狗设置 60 秒总时限。因此，已经开始生成、仍在返回工具参数的长响应也可能在第 60 秒被中断。HTTP 层先超时时，看门狗标记尚未设置，还会将 `HttpTimeoutException` 归类为网络中断。

现在流式请求使用独立 HTTP 客户端及以下配置，普通 JSON/向量请求保留原有超时：

| 配置 | 默认值 | 行为 |
|---|---:|---|
| agent.model.stream-timeouts.first-byte-seconds | 120 秒 | 从请求开始等待首个响应体字节 |
| agent.model.stream-timeouts.idle-seconds | 90 秒 | 收到字节后，连续无新字节达到此值才中断 |
| agent.model.stream-timeouts.max-duration-seconds | 600 秒 | 单次请求总时限，不能被心跳无限延长 |

计时使用单调时钟；统计原始读取字节，包括 SSE 心跳、工具参数和不会公开的模型推理字段。不保存或公开私有推理内容。首包指响应体字节，HTTP 响应头不算首包。无正文输出但持续收到心跳时，最终仍受单次请求总时限约束。

任务整体截止时间、停止和暂停仍优先。超时/取消会关闭流并清理工作线程的中断标记，避免影响后续数据库清理。原生 HTTP、Socket 及嵌套超时统一映射为安全的 `MODEL_TIMEOUT`，普通断连仍为 `MODEL_NETWORK_ERROR`。

连续三次失败仍持久化暂停，不无限重试，不自动重放结果不明的外部写操作。模型配置检测单独限时 90 秒，保持在前端 120 秒等待范围内；长任务不会继承此检测上限。

## 输出截断与用量

单次输出上限从 2000 调整为 8192 Token，这是上限而非固定消耗；任务总额度保持不变。推理模型的推理与可见回答可能共享输出额度，长文稿还需分批生成以减少重复输出。参见 [MiMo 官方说明](https://mimo.mi.com/docs/en-US/quick-start/usage-guide/other/deep-thinking)。

`finish_reason=length` 映射为 `MODEL_OUTPUT_TRUNCATED`；缺失完整结束标记映射为 `MODEL_INVALID_RESPONSE`。两者不再冒充 `ask_user`，不执行半截工具参数，并按连续失败策略有限重试。已返回的提供商 usage 随异常传递并准确结算，只有用量未知时才保守处理。已知失败结算先通过数据库状态条件抢占一次，避免重复计入任务 Token。

## PPT 文件交付

长文稿使用 `presentation_create` 与 `presentation_append` 分批构建完整可编辑 PPTX，减少单次工具 JSON 长度及重复输出。PPTX 文件卡片提供查看及下载入口，预览页面从对应文件渲染，不以大纲或独立 PNG 代替 PPTX。

## 验证入口

- `StreamTimeoutBudgetTest`：虚拟时钟检查首包、空闲、总时限及嵌套错误分类。
- `StreamingChatTest`：实际 HTTP SSE、取消/空闲流关闭、完整结束标记及 usage 保留。
- `FileToolsTest`：追加到 12 页、原文件字节不变、原生图表和讲稿保留、末页渲染、非法批次及无权文件拒绝。
- `node scripts/verify-stream-timeouts.mjs`：两个真实 65 秒 HTTP 夹具，验证延迟首包与持续流式输出，不花费提供商 Token、不修改保存的模型。
- `node scripts/verify-output-recovery.mjs`：两次截断后第三次恢复、连续三次截断后暂停、无补充问题与不完整工具副作用；三个响应均按真实报告的 168 Token 结算为 504。
- `node scripts/verify-file-tools.mjs` 与桌面 `verify-file-tools.cjs`：真实后端文件创建、下载、逐页预览及对话文件卡片。
